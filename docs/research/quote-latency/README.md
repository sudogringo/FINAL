# Quote latency baseline (VD2)

Standalone scripts to measure **VD2 — Eficiencia operativa del proceso de leads** (§3.2): the
end-to-end time from a customer submitting a quote request to the sales team being notified,
against the local demo stack. Not a workspace member of `frontend/` or `backend/`; run
independently.

## What this measures

VD2's design criterion (§3.2) is "≤15 segundos... entre la recepción del webhook con la solicitud
de cotización y la entrega de las notificaciones al equipo de ventas". Concretely, the path
instrumented here is:

```
Frontend: user clicks "Enviar solicitud" (T0, clientSubmittedAt)
  -> POST /api/quotes (backend: validates, upserts Customer, creates Quote)
    -> backend fires N8N_QUOTE_WEBHOOK and (in measurement mode only) awaits it
      -> n8n workflow "00. Lead Notification" (🟢 TESIS branch) runs:
         builds the notification message, sends it via Gmail, records t1_end
      -> n8n responds to the backend with t1_start/t1_end
    -> backend returns { id, receivedAt, n8n } to the caller
```

`endToEndLatencyMs` = `n8n.t1_end - clientSubmittedAt`. This is the number that maps onto §3.2's
criterion — not the backend's internal processing time alone, which is a much smaller sub-interval
of this and not what §3.2 defines.

## Why this needed a workflow to be built first

As of this baseline, no n8n workflow existed at the `N8N_QUOTE_WEBHOOK` path
(`/webhook/quote`) — the backend's fire-and-forget call to it was a no-op in a standard run
(`N8N_QUOTE_WEBHOOK` unset by default in `docker-compose.yml`). `n8n/workflows/00._Lead_Notification.json`
was added specifically to close this gap, following the same dual-branch pattern as the other
workflows: a 🟢 TESIS branch that actually runs (Gmail to the author's own inbox, no paid APIs) and
a 🔴 PRODUCCIÓN branch (WhatsApp Business API + SendGrid) left disabled with placeholder
credentials, matching `n8n/workflows/07._Logistics_Shipping_Automation.json`'s structure.

## Methodology

- **Demo mode only**: every run uses synthetic data generated by `fixtures.mjs` (fake names, fake
  `@example.test` emails, fake phone numbers, catalog product IDs) — no real Golden Harvest data,
  per the project's "no real access, everything simulated" constraint.
- **15–20 runs per batch**: a single request is one sample of a system with real variability
  (DB write time, n8n cold-start on first execution, Gmail API round trip). Reporting median +
  min/max + p95 across a batch gives a defensible answer instead of a single anecdotal number.
- **Measurement mode required**: the backend's default behavior is fire-and-forget (it does not
  wait for n8n, by design, so the customer-facing response stays fast). To measure the real
  end-to-end latency, the backend must run with `MEASURE_LATENCY=true`, which makes it `await` the
  n8n webhook and return its `t1_start`/`t1_end` in the HTTP response. This is a measurement-only
  code path — it does not change default production behavior.
- **Stack must be fully up**: Postgres + backend + n8n via `docker compose up`, with the
  `golden_harvest_api:8000` hostname bug already fixed in
  `n8n/workflows/05._Monthly_Activity_Report.json` and `07._Logistics_Shipping_Automation.json`
  (fixed as part of this same round of work — unrelated to VD2 but was blocking other
  end-to-end checks).

## Setup

```bash
cd docs/research/quote-latency
# no external dependencies — plain Node with global fetch (Node 18+)
```

## Running a batch (playbook)

**Trigger**: any change to `backend/src/routes/quotes.ts`, `n8n/workflows/00._Lead_Notification.json`,
or the frontend's quote-submit path that could move this latency.

```bash
# 0. From repo root.

# 1. Start the full stack.
docker compose up -d
# confirm backend, n8n, postgres are healthy:
docker compose ps

# 2. Backend must be running with MEASURE_LATENCY=true for this batch.
#    Either set it in docker-compose.yml's backend service temporarily, or run the
#    backend locally instead: cd backend && MEASURE_LATENCY=true npm run dev

# 3. Import/activate n8n workflow "00. Lead Notification" (🟢 TESIS branch) at
#    http://localhost:4343 if not already active — see n8n/README.md for import steps.

# 4. Archive any existing batch with the same label before re-running (see "Why archive
#    first" below) — run-batch.mjs refuses to overwrite a non-empty batch directory anyway.

# 5. Fire the batch (18 runs is the default; adjust with --runs).
cd docs/research/quote-latency
node run-batch.mjs --runs=18 --label=<date-or-shortsha>

# 6. Aggregate.
node summarize.mjs
```

### Why archive first

Same discipline as `docs/research/lighthouse/`: a batch is only internally consistent if every run
came from the same code (backend + workflow version). `run-batch.mjs` writes into
`results/batch-<label>/` and refuses to run again into a non-empty directory — pick a new
`--label` (date or short commit SHA) for a new batch rather than deleting the old one, so past
batches stay available for before/after comparison.

### Sanity checks after step 6

- `results/summary.csv` has one row per batch, with `n_failed` at or near 0. Any failed run means
  either `MEASURE_LATENCY` wasn't set, the n8n workflow wasn't active, or the Gmail credential
  wasn't configured — not a real latency data point, and must not be silently dropped into the
  median calculation as if it succeeded (it isn't — `endToEndLatencyMs` is `null` for those and
  `summarize.mjs` excludes them, but a batch with many failures is not a valid measurement).
- `results/batch-<label>/run-*.json` — spot check a couple of files: `n8n.t1_end` should be after
  `n8n.t1_start`, which should be after `clientSubmittedAt`.
- `summary.json`'s `meets_criterion` field states plainly whether the median is ≤15000ms — report
  this as-is in the thesis, whichever way it comes out (no rounding in the favorable direction).

## Output

- `results/batch-<label>/run-<n>.json` — one file per request: timestamps, HTTP status, and either
  `endToEndLatencyMs` or an `error`.
- `results/summary.json` — one entry per batch: `median_ms`, `min_ms`, `max_ms`, `p95_ms`,
  `n_failed`, and `meets_criterion` against the 15000ms criterion from §3.2.
- `results/summary.csv` — same data, one row per batch, for import into a spreadsheet/pandas.

This directory only produces the measurement artifacts. Whether/how this result is written into
the thesis is a separate, explicit step — not part of what these scripts do.
